## 二、问题清单

### 1. 加载与解析成本

**P1零懒加载：19 个 script 块全部在首屏解析执行，约 85% 是用户可能永远不打开的数据。**
外部资源引用 0（无 src script、无 link、无 CDN），单文件在解析过程中逐块阻塞执行。数据以 JS 对象字面量内嵌（解析成本高于等量 JSON.parse 字符串路径），ET 一区就是 3.06M 字符。孩子只点开拼读区，也要先付清词源+介词+词库的全部解析费。

**P2介词区一个视图吞掉 3.95M 字符静态 HTML + 58 张内嵌图。**
`#v-prep`（行 4261–4629）单视图 3,952,069 字符 = 全部静态 HTML 的 93%；其中 58 个 base64 媒体共 3,884,244 字符。全文件共 66 个 base64 块（65 JPEG + 1 MP4，约 4.99M 字符 ≈ 文件的 27%），另 8 个（1,106,852 字符）在 PK 的 JS 数据里。base64 比二进制膨胀约 33%，不能独立缓存、不能按需取用；介词区首次显示时 58 张图集中解码，有内存峰值风险。静态 DOM 全文件约 8,000 个元素（v-prep 占 1,775 个标签、字符占 93%——胖在属性里的图，不在结构）。

**P3分发与更新成本：无缓存拆分。**
文件近 8 天被提交修改 72 次（见 §4）。若走网络分发，每次更新都是全量 18.66MB 重下，无 gzip 分片、无按区缓存；若本地打开（file://），则是每次冷启动全量重解析，二选一都付全价。

冷启动估算（未实测）：中端安卓机上 10.16M 字符 JS 解析 + 数百万数据对象构建 + 约 8,000 元素初始 DOM + 多区启动预渲染（见 P4），冷启动进入可交互大概率为秒级（2–5 秒量级估算）。目标用户是小学生家庭的手机/平板，这是全篇最贴身的风险。

### 2. 渲染与运行模式

**P4启动时全渲染：多个大区在 App 启动时就把索引 DOM 建好，与访问无关。**
实证（各 IIFE 结尾直接调用）：VC 块尾 `renderList();`、ET 块尾 `renderIndex();`、MORPH 块尾 `renderIndex();`。PN/AR/CJ 的首页 section 静态内容只有 242–325 字符（空壳），而全局 `show()`（行 5750）只切 class、没有任何区级渲染钩子，所以这三区的索引也只能由各自 IIFE 在启动时预渲染（与 ET/MORPH 同模式）。好的一面：各区**详情页**多为进入时渲染（detail section 静态 64–84 字符空壳），内耗集中在索引层。`innerHTML` 赋值全文件 303 处。

**P5动画计时器清理不齐：4 区有统一清理，3 区靠自理。**
全文件 setInterval 仅 3 个、setTimeout 38、rAF 22，绝对量不大。MutationObserver 离场清理已注册的区：VB（行 9947）、PN（13262）、AR（14401）、CJ（15513）——都观察自己 section 的 class 变化停表。没有 MO 的动画持有者：GK 语法（setInterval 1 个，无 MO，靠 clearInterval 自理）、PK 介词（rAF 7 + setTimeout 5，无 MO，clearTimeout 仅 1 处）、FA 旗舰白板（行 10892 块，setTimeout+rAF，无 MO、无 clear）。rAF 按文档可见性节流、**不按元素可见性**：section 被 display:none 后 rAF 链仍继续跑、继续写隐藏 DOM——不会崩，但是真实的后台耗电与无效计算，且各区标准不一，后来者容易漏挂。

其余运行面健康项：CSS 动画 16 个 @keyframes、6 处 infinite，量级可控；transition 22 处、box-shadow 30 处、固定定位仅 1 处，未见滚动劫持类热点；无 document.write、无 eval。

**P7全局命名空间半污染，块间靠全局变量隐式耦合。**
好的一面：新区都收敛为 `window.XX`（共 12 个：VC/ET/GK/PK/VB/PN/AR/CJ/FA/RV/TN/say）。坏的一面：早期块留大量裸全局——VC 块的 WLIST/GROUPS/PHG/WPAGE/MZLAND/MZPAGE 与裸函数 vcShow/openCard/goPhon 等；LAWDATA 块（行 5066）的 `LAW`/`LAWDATA` 被跨块引用 30 次；H2 块在启动时把 PHONLAWS 用 Object.keys **运行时并入** LAWDATA（行 5190 块尾）——数据拼装发生在用户设备上。复习引擎的题库 buildPool() 也是运行时跨模块组装。后果：删/改一个块的全局名，会静默打断别的区，没有任何编译期检查能拦住。

**P8裸元素 CSS 只剩两处，但都在要害位置，且新区移植税持续存在。**
行 7 的全局样式块含 `header{background:linear-gradient(…)}`（已知坑：任何移植区块的裸 `<header>` 都会被涂成横幅，已实际发生 2 次）和 `*` 通配规则；figma-all 块（行 15563）含全局 `img,canvas{max-width:100%}`。其余区的样式已普遍作用域化（23 个 style 块、133K 字符，主体是 `.xx-scope`/`.xxmod` 前缀），风险面收敛但未清零。

**P9内联事件存量大：onclick 794 处（on* 属性 777+），与事件委托并存。**
全局委托已建立（show 块处理 data-go/.nbtn/.opt，LAWDATA 块处理 data-law/data-say），但各区模板字符串仍大量生成 `onclick="XX.fn()"`。后果：无法启用 CSP；函数改名必须全文搜替；手误写错一个处理器名只在点击时才暴露（今晨审计的 pageerror 横扫只能覆盖被点到的路径）。

**P10CSS 双层制：各区自带配色 + figma-all 末位覆盖层（行 15563，9,960 字符）靠顺序与特异性压制。**

### 4. 可维护性

**P11单文件 15,699 行 / 18.66MB 是双线并行的冲突主战场，且数据行不可人工审阅。**
git 实测：2026-10-27 至今仓库 633 次提交，其中主文件 72 次（约 9 次/天）；近期历史有 ≥5 个 merge 提交（bb9a7dd、6f5e714、bf8e181、9f5816e、8b1f9c4…）。已发生的实证事故：用户侧陈旧副本推送曾把词源 payload 静默回退到 801/1477 旧版（靠 rebase 冲突才暴露）；本日色板对齐又遇推送竞速、靠 cherry-pick 重落。ET payload 等数据是单行数 MB 的巨型行，冲突时 git 只能整行二选一，人眼无法审。

**P12生成链不在仓库内，同步靠人肉与外部脚本。**
仓库内找不到任何生成脚本（仅 docs/home/home_entries.py 与数据无关）。现状同步关系：① 同一份词库/LAWREG 数据须在主文件与 `morphology-prototype-v1.html` 两处**字节一致**（该镜像文件同期也有 5 次提交）；② 词源数据三处存放（model/etymology.json → 主文件 ET payload → 独立原型），刷新脚本 refresh_et.py 存在于仓库外的 ~/workspace/mengxing-etymology-prototype/；③ model/laws/*.yaml → LAWDATA 的并入是 H1/H2 人工波次，无可复现构建步骤。换机器、换人、或外部目录丢失，生成链即断。

**同步点实测例**：新增一个区要改 ≥7 处——导航 pill、首页卡、首页区数文案、section 骨架、作用域 CSS、figma-all 色板映射、计时器清理注册（连词区集成 diff 1,225 行实测；其色板对齐又是独立一轮 11 点编辑）。

### 5. 容错与恢复

**P13块间有解析隔离，但运行时零兜底：一个区启动抛错 = 该区静默空白。**
19 个 script 块独立解析，一块的语法错不会拖垮其他块（单文件多块的意外红利）。但全文件没有 window.onerror 处理器（唯一的 onerror 在行 9365，是语音识别回调）；各区 IIFE 在启动时执行渲染（见 P4），任一 IIFE 抛错，该区即空白且无降级提示、无重试入口、无上报——家长和孩子只会看到「这个区打不开」。

**P14跨块单点依赖两处。**
① 全局 `show()`（行 5750，块仅 1,919 字符）是 61 个视图导航的唯一入口——块小且独立，风险低但确实单点。② `LAW/LAWDATA`（行 5066 块）是规律页渲染、data-say 朗读、复习引擎题库的共同依赖，该块损坏的波及面跨 3 个区以上。

**P15localStorage 面小且读写有防护，但版本升级 = 进度静默清零。**
全 App 只有 2 个子系统落盘：VB 的 4 个键（`mx_vb_srs_v1`、`mx_vb_loop_v1`、`mx_vb_log_v1`、`mx_vb_lifeline_v1`，行 8927/9132/9281/9840）与复习引擎的 `mxReviewV1`（行 10599）。防护做得对：VB 的 lsGet/lsSet 带 try/catch + 内存兜底（行 8922–8924）；复习引擎读入校验 `p.items && p.wrong` 形状（行 10603）；日志键有 600 条上限自清理。缺口：版本管理只有键名后缀（_v1/V1），将来数据模式升级只能换新键，老进度（SRS 盒子、复习队列、家长报告数据）无迁移路径、静默归零；除日志外其余键无体积/配额管理。

**离线与弱网**：零外部资源 = 天然全离线可用，这是单文件架构对目标场景（家庭设备、可能无网环境）的真实优点，应予肯定。弱网风险只发生在网络分发模式：单请求全有全无，无 Service Worker、无分片续传，18.66MB 中途失败即整个 App 不可用。

## 三、架构层最该先动的 3 件事

1. **数据与代码分家，先砍冷启动解析量。** ET（3.06M）+ VC（1.46M）+ PK（1.45M）三块约 6M 字符改为「JSON 字符串 + 进入该区时才 JSON.parse」的惰性数据，或拆成延迟执行的数据块；介词区 58 张图（3.88M 字符）改为进入介词区时才注入 DOM。目标：冷启动必付解析量先降一半以上，且不动任何教学内容。

2. **把生成链收进仓库并加一致性校验。** refresh_et.py、LAWREG/词库双文件字节一致校验、yaml→LAWDATA 并入，固化为仓库内一键脚本 + 提交前（或 CI）自动校验：双文件 DATA 不一致、计数口径过期（如首页卡「547 条」类）直接报错。直接对症已发生过的静默回退事故与双线合并竞速。

3. **收编公共层五件套，并统一动画离场清理与错误兜底。** esc / say / 白板播放器 / 大人说明折叠 / quiz 判题各留一份公共实现（存量 11/6/4+2/5/3 份冻结新增、按区逐步归一）；GK/PK/FA 补上与 PN/AR/CJ 同款的 MutationObserver 离场清理；加一个 window.onerror 兜底，让坏区显示重试入口而不是空白。
