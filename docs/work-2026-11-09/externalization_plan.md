## 2. `file://` 约束核查（实测，非想当然）

外置方案成立的前提是：双击打开（`file://`）时，相对路径的经典资源引用可用，而 `fetch()` / ES module 不可用。先核查现文件是否已依赖任何 `file://` 下会失效的机制——**结论：没有**，所以外置不会“破坏一个本来就依赖服务器的功能”。

| 检查项 | 实测结果 |
|---|---|
| `fetch(` 调用 | 1 处，但**在词源文本字符串里**（Etymonline 原文引用英文单词 fetch），不是代码调用。代码中 `fetch` 为 0 |
| `XMLHttpRequest` | 0 |
| ES module（`type="module"` / `import(` / `import` 语句） | 0（17 处 `import` 全是 `!important`、英文单词或注释里的 `imported/`） |
| `new Worker` / `importScripts` | 0 |
| `document.write` | 0（加 `defer` 也不会踩雷，但本次方案不用 `defer`，见 §3.3） |
| `document.currentScript` | 0（外置后脚本自引用方式不变，无影响） |
| `location.protocol` / `file://` 判断 | 0（代码不区分协议，外置不改变行为） |
| `DOMContentLoaded` 监听 | 7 处（与外置无冲突，经典脚本按序执行时仍能注册到） |
| `speechSynthesis`（点读） | 29 处，与文件组织无关，不受外置影响 |
| `localStorage`（`mengxing_v1_1_state` 等） | 与文件是单文件还是多文件无关，不受外置影响 |

浏览器行为口径（实施前须在 Chrome / Edge / Safari 真机上逐项验证，见 §5）：

- ✅ `file://` 页面用**相对路径**加载同目录或子目录的 `<img src>`、`<script src>`（经典脚本）、`<link rel="stylesheet">`、`<video src>`：Chrome、Edge、Firefox、Safari 均允许。解析基准是 HTML 文件所在位置，与双击时的工作目录无关。
- ❌ `file://` 下 `fetch()` / `XMLHttpRequest` 读本地文件：Chrome、Edge 拦截（CORS）；Firefox 仅放行同目录部分情况，不可依赖。
- ❌ `file://` 下 ES module（`type="module"`、`import`）：按 CORS 处理，Chrome、Edge 拦截。
- ❌ `file://` 下 `async` / `defer` 虽不被拦截，但会改变脚本执行时序（见 §3.3），本次不用。

### 关于 E（白板）的特别说明：README 的描述已过期

README“修改注意”称白板模块在文件末尾的 `<script type="text/plain" id="wbmod-…">` 里、第一次进入对应页面时才执行。但实测 HEAD：

- `wbmod` 出现 0 次，`text/plain` 出现 0 次，`insert_wb.py` 全仓不存在；
- `docs/whiteboard/src/` 84 个条目中只有 2 个 `.js`（`fnranges.js`、`vocab_extract.js`），其余是检查/生成脚本；`wo_hub.js`、`ze_hub.js` 不存在；
- 白板代码已是普通同步脚本（块 #10、#33、#39 等），**所谓“按需加载”在当前 HEAD 不成立**，白板随页面一次解析。

结论：外置时不要按 README 的旧描述去找 `wbmod` 块拆分；以实测的 41 块为准，白板随 D1 整块外置。`docs/whiteboard/SOP.md` 与 README 的白板工作流描述应在实施前由白板负责人核对更新，否则后人会按过期文档改错地方。

### 关于 D1 的三条硬规则（违反即破坏功能）

1. **顺序**：41 个外置脚本的引用顺序必须与原文件内块的顺序完全一致。`LAWDATA`（#08）须在引用它的块（#00、#05、#09、#12、#19、#20、#25、#32、#34、#35）之前；#09、#20 在加载时向 `LAWDATA` 合并数据，须在 #08 之后、使用者之前。`LINKIDX`（#05）须在 #00 之前。
2. **不加 `async` / `defer`**：两者都会让脚本执行脱离文档顺序。`defer` 虽然保持相互顺序、且无 `document.write`，但会把全部脚本推迟到解析完成后执行——当前有脚本在解析中途就操作已解析的 DOM、注册全局处理器，改时序须逐块验证，不值得为“首屏不阻塞”冒这个险。外置的第一目标是“行为零变化”，不是“首屏最快”。
3. **不用 ES module、不拆块内结构**：块内数据与代码同处一个 IIFE 或共享顶层 `var`（如块 #06 的 `D` 与渲染器同块、块 #00 的 `WLIST` 与词页渲染同块），把数据从块里抽出来单独成文件会切断闭包/同块引用。**只允许整块搬运，不允许块内拆分。**

## 4. 实施方案

### 4.1 总体结论：不需要改服务器模式

推荐方案全程使用相对路径的经典引用（`<img src>`、`<video src>`、`<link>`、`<script src>`），**双击即用保持不变**，不需要起静态服务器。

但有一个真实的代价必须写在前面：**外置后“单文件随手转发”的特性丢失。** 现在可以只发一个 HTML 文件给别人；外置后只发 HTML 会丢图、丢视频、丢数据，页面会报缺失文件。分享方式改为“整个 `laws-prototype/` 文件夹打包（zip）再发”，README 必须补这一句（见 §6.1）。如果 Priya 认为“单文件可转发”不可丢，则本次外置只能做 A/B/C 三类（图片+视频，共 4,992,613 字节、21.4%），D1/F 不做——这个取舍由她定。

诚实说明外置的收益边界（避免过度承诺）：

- 外置后首次打开仍要解析 18.7 MB 的 JS（只是从“解析一个 23 MB 文档”变为“解析一个 0.6 MB 文档 + 41 个 JS 文件”），JS 编译总量不变；**首屏解析耗时不会等比下降**，下降的是 HTML 解析阻塞与 5 MB base64 的解码成本，首屏出现会明显提前，但不是“从 23 MB 变成 1 MB 就快 20 倍”。
- 真正的二次打开加速依赖浏览器缓存；`file://` 的缓存行为不如 HTTP 可靠、不可写进承诺里。想稳定地获得缓存收益与按需加载，才需要服务器模式——那是 D2 路线，不在本次方案内。
- 外置的确定收益：主文件从 23.35 MB 降到约 0.6 MB 壳；图片懒加载真正生效；视频不再整段 base64 解码；JS/CSS/图片可独立更新、独立校验；为将来上服务器 + 按需加载铺好了文件结构。

### 5.2 启动自检脚本（留在壳里，< 2 KB）

放在全部 `<script src>` 引用之后、内联：

```html
<script>
(function () {
  var need = ['LAWDATA', 'LINKIDX', 'PK_PH'];  /* 按依赖顺序列关键全局变量 */
  var missing = need.filter(function (k) { return typeof window[k] === 'undefined'; });
  if (missing.length) {
    document.body.insertAdjacentHTML('afterbegin',
      '<div style="background:#fff3cd;color:#7a5b00;padding:12px;font-size:15px">'
      + '萌星英语未能完整加载：缺少数据文件（' + missing.join('、') + '）。"
      + '请确认 laws-prototype 文件夹完整（assets 文件夹须与本文件放在一起），不要只单独复制本文件。'
      + '</div>');
  }
})();
</script>
```

要点：只报“缺了什么、怎么办”，不报技术细节；图片缺失另由 `<img onerror>` 兜底为占位图（第 1 步做）。

### 5.3 回退方案

1. **每步可独立回滚**：每步一个提交，任何一步验证失败直接 `git revert` 该提交，主文件与 `assets/` 一起回到上一步。不要跨步混提。
2. **单文件版保留**：外置实施不删除 git 历史里的单文件版（HEAD `e97aaec` 的原文件永远可取回）。第 4 步另写 `tools/build_single_file.py`（把 `assets/` 拼回单文件，用于发布单文件版），但**本次任务不做该脚本**，只留接口位置；在这之前，回退手段就是 `git revert` / 从历史取回原文件。
