# 萌星白板动画全量重写 · 技术方案与 SOP

> 决策依据（2026-11-01，用户拍板）：全部重写，逻辑不对的内容也重写；因需经常修改，**可维护性为第一设计原则**；采用「知识模型单源 + 多视图渲染」架构（不作远期，即刻采用）。
> 输入清单：《「第一性原理」理论清点报告》（first-principles-audit.md）为内容纠错 fix-list；《布局 QA 方案》《动画技术升级方案》为表现层输入。

## 1. 要解决的问题

| 病灶 | 证据 |
|---|---|
| 同一事实多处副本，改一处要 hunt 全仓 | 「物理边界」同存于 DB、分镜、场景 KNOW、要点卡四层；② 的 DB 串入 ③ 的内容 |
| 理论错误以「定律」名义入库，无闸门 | 24 幕审查：错误 3、过度简化 5（见清点报告）；机制故事冒充原因 |
| 场景是手写编排代码，改动贵且易错 | 坐标散落近十处、时长手算对齐、无节拍对象；补丁式修改多次出错 |
| 逻辑错误靠人眼事后发现 | 两个整苹果、「没边」判据均为交付后由用户指出 |

## 2. 总体架构（四层 + 一引擎）

```
知识模型层（唯一事实源）  ← 全部教学内容只存这里，带类型/证据/例外
      ↓ 引用 ID
模式层                    ← 教学模式（骨架）+ 语义原语 + 锚点/分区 + 选角注册表
      ↓ 组合生成
视图层                    ← 白板场景 / 要点卡 / 口诀卡 / 测验 / 复习题，多视图同源渲染
      ↓
验证层                    ← 入库校验 + 例外冲突检查 + insightcheck + 截图回归 + 逻辑审查
      ↓
引擎层（不变）            ← wb5 渲染引擎与播放器保持不动
```

核心原则：
- **场景是产物，不是工件**：由「内容 × 模式」生成；产物不维护，改源头后重新生成。
- **文案零副本**：任何上屏文字必须引用知识模型中的记录 ID，场景文件内禁止自带 KNOW 副本。
- **少数旗舰幕**可用声明式节拍精调，但文案仍引用 ID、布局仍用锚点。

## 3. 知识模型设计

存储：仓库内结构化数据文件（YAML，一条记录一个条目，git diff 友好、人可直改），配 JSON Schema 校验脚本；构建时编译为 JS 数据供生成器使用。

### 3.0 领域纲领（先有高屋建瓴，再有逐条数据）

数据不是碎片的堆积：每个知识领域先立一条**纲领**（Domain Insight），再往下挂概念与主张。纲领 = 一句能统摄该领域大多数规则的核心看法（例：冠词领域的纲领是「冠词是说话人指给听话人看的动作」；可数性是「形式跟着看法走」）。纲领记录字段：coreView（核心看法）、unifies（它统摄的 Concept/Claim ID 列表）、conflicts（与之冲突的旧框架，点名）。入模顺序铁律：先纲领、后概念、再主张——审查发现的每条数据必须能挂到某条纲领下；挂不上的，要么纲领要扩写，要么这条数据本身可疑，人工裁决。动画表达以纲领为纲：每幕先声明所属纲领，概念呈现从纲领展开到细节，杜绝「每条规则各编一个故事」的碎片化讲解。

### 3.1 实体

| 实体 | 说明 | 关键字段 |
|---|---|---|
| Concept（知识点） | 一个教学点，如「可数性识解」 | id、名称、年级、课标锚点 |
| Claim（主张） | 一条可上屏的说法 | id、type（见 3.2）、陈述句、适用范围 |
| Example（例证） | 支持主张的真实例句/词 | text、gloss、supports→Claim |
| Exception（例外） | 主张的已知例外 | text、说明、exceptionOf→Claim |
| Chant（口诀） | 助记韵文 | text、for→Claim、性质标注（规则/联想） |
| Asset（素材） | 角色帧/道具 | id、语义标注（姿势实况，沿用 CAST 注册表） |

关系：prerequisite（先修）、contrastsWith（对比）、exceptionOf、supports。关系使「先学什么」与「改一条牵连哪些」都可计算。

### 3.2 主张分型（防理论错误复发的核心闸门）

| type | 定义 | 必填字段 | 命名禁令 |
|---|---|---|---|
| rule（真规则） | 无例外或例外可枚举的范畴性规则 | statement、examples≥2 | 可用「规则」，仍禁用「物理定律」类措辞 |
| tendency（统计倾向） | 大多数情况成立的规律（如音缀、介词维度） | statement、examples≥3、**exceptions≥1**、scope | 禁用「律/一律/永远」；上屏必须带「大多数/一般」 |
| mnemonic（记忆联想） | 为记忆而编的图画/故事（字母象形、守门员） | statement、**linkedClaim**（它帮记的真内容）、联想说明 | 上屏必须标「可以想成/帮你记」；禁称「来源/本源/同源」 |
| etymology（真词源） | 有词源学依据的来源 | statement、来源语与原义、examples | 必须可溯源；无把握者降为 mnemonic |

校验器硬规则：tendency 无 exceptions 字段 → 入库失败；mnemonic 无 linkedClaim → 入库失败；任何 Claim 的 statement 含「物理定律/统摄律/绝对」等词 → 报警人工复核。

### 3.3 讲法字段（深入浅出是数据的一部分，不是临场发挥）

每条 Claim 必填 `explain`（讲法）字段，与 statement 同级入库、同样过审：

- **方法**（枚举，至少选一）：对比案例（最小对立）/ 功能目的（这个形式是干什么活的）/ 说话人—听话人视角 / 镜头—看法框架 / 类比 / 动作体验 / 分层递进（先生活版、后准确版）。
- **载体**：讲法所用的比喻、故事或动作，一句话写清。
- **失效边界**（用类比/隐喻时必填）：这个比喻在哪里不像、到哪里为止——缺此字段不得入库。教训：旧数据大量用「物理化隐喻」讲语法（边界、外壳），抓人但机制是假的；新规矩是隐喻可以留作 mnemonic，但承载概念的框架必须是真机制（如可数性用「看法/镜头」，冠词用「说话人指给听话人看」），且每个隐喻自带边界声明。
- 一个概念至少两种表征互证（如图示 + 动作，或故事 + 对比案例），单一隐喻不得独占一个概念。

全量内容审查（2026-11-01）按此标准同步产出「讲法升级清单」：概念错误者换框架，概念对但讲法差者换讲法，二者与裁定清单同为入模型门禁材料。

### 3.4 例外即测试

每条 Exception 同时是回归测试：校验阶段把全部例外与主张陈述做冲突扫描（先用关键词/人工清单，逐步自动化）；修改一条 Claim 时，构建系统列出其全部例外与引用方视图，要求修改者逐项确认不冲突，方可入库。

## 4. 模式层

- **教学模式目录**（骨架有限收敛）：钩子问错 → 演示 → 对比 → 预测 → 命名规则 → 回顾卡，每种模式定义节拍槽位与必填/可选槽。
- **语义原语**（受约束、防逻辑错误）：cut（一个物体→带切面的两半，守恒由构造保证）、pour（体积守恒的液体）、countWith（先容器后计数，徽章只能由容器产生）、attachSuffix（-s 只能贴在单位/容器词上）、predict、contrastPair 等。原语内部实现沿用动画技术升级方案（解析弹簧、程序液体、粒子）。
- **语义标签**（2026-11-01 用户拍板新增）：每个元素与原语实例在场景数据中带语义标签（出口 / 容器 / 单位 / 主体 / 切面…），标签随生成数据流动、可在截图与日志中定位。构建期断言（第 6 节第 1 项）只引用标签做关系检查，不认裸坐标——坐标改了断言不失效，关系改了断言必报警。
- **锚点与分区**：沿用布局 QA 方案的舞台分区表与锚点命名（STATION/ZONE），元素只挂锚点，坐标只在锚点定义处出现一次。
- **选角注册表**：沿用 CAST 语义注册（姿势实况标注），场景按语义选角（standing/clean），不按文件名猜。
- **动作事实卡与参照库**（2026-11-01 用户拍板新增）：每个含物理动作的原语（pour / cut / 装杯 / 撕纸…）挂一张「动作事实卡」——从真实参照照片/视频提炼 3–5 条因果事实（出口位置与朝向、接触关系、先后顺序、结果状态），参照图存入仓库并在卡上登记 ID。事实卡是原语的实现约束，也是第 6 节参照对比审查的核对表。教训来源：咖啡壶事件——几何上「液柱接到壶嘴尖」不等于因果成立，壶嘴轴线朝上时液体根本流不出（倾角须使轴线朝下、出水在倾斜到位之后、停水在回正之前）。

## 5. 生成与视图

- 生成器：模式 × 内容记录 → 场景数据（节拍数组）→ 现有 build 流程 → 单文件 HTML。节拍时长由旁白文本按既有公式推导，退场用相对式（下一节拍前 0.4s），禁止手写绝对对齐时间。
- 多视图同源：同一 Concept 可渲染要点卡（HTML/PDF）、口诀卡、测验题、复习条目；视图只读模型，不回写副本。
- 旗舰精调：声明式节拍文件覆盖生成结果中的指定节拍（override 按节拍 ID），文案仍引用 ID；override 需在文件头声明理由，纳入审查。

## 6. 验证层（交付门禁，缺一不出货）

1. 内容与构建校验：schema + 3.2 硬规则 + 例外冲突扫描，全过才可构建；构建后自动跑**不变量断言**（2026-11-01 新增，按语义标签做关系检查，任一失败即阻断交付）——示例：液柱起点距「出口」标签点 ≤10px 且出水时段内出口朝向朝下；cut 两半的面积和与原物体偏差 ≤5%（守恒机器化）；计数徽章数值 = 画面「容器」数；字幕区与说词区零重叠。断言库随原语增长：每修一个因果错误，必须留下一条能抓住它的断言。
2. insightcheck：项目原检查器，不合格 0（保持现有门禁）。
3. 截图回归：固定时刻截图集与基线对比，变化需人工确认后更新基线。
4. 逻辑审查：交付前独立一遍（可由子代理执行），按五项清单过截图——守恒 / 同一 / 因果 / 指称 / 时序；事实表由内容模型自动生成草稿（物体、类别、状态变化、称呼规则），审查对照之。
5. 参照对比审查（2026-11-01 新增）：凡含物理动作的节拍，审查时将动画帧与该动作的参照图**并排**，逐条核对动作事实卡（出口位置与朝向 / 接触 / 时序 / 结果状态）；任一条不符即打回，修正落在原语或规格层（一处修改、全家族生效），重建后复检该帧。截图回归（第 3 项）查「变没变」，本项查「对不对」，不可互相替代。
6. 改动任务测试（可维护性验收，试点与大版本必跑）：换台词、挪站位、换素材、加一拍、改判据五种改动，各须在**一个文件、一处编辑**内完成并通过 1–5。
7. 儿童误读探针（2026-11-01 新增，旗舰幕验收专属）：试看者（目标年龄段儿童；无条件时由未参与编写的成人按儿童视角复述）看完一遍后复述判据，并回答针对该幕已知误解点的探针问题——问题从模型例外与审查观察中生成（如「米粒一颗颗的，为什么不说 rices？」）。判读标准：复述把判据说反、或探针答错，即不通过，问题归因到台词/画面后按 8.1/8.3 修正再测；通过的探针问题入库，成为该幕的回归探针，后续改动复跑。

## 7. 迁移计划（分期，每期独立验收）

- **P0 基础设施**：知识模型 schema + 校验器 + 生成器骨架 + 视图模板（场景/要点卡/测验各一）。存量盘点：558 幕按模式归并统计（骨架种类数、重复场景清单），输出归并表——决定 P3 的实际工作量。
- **P1 试点纵切（③ 家族）**：按清点报告 P0/P2 改法重建 ③ 的内容记录（识解判据、例外齐备）；生成 fp_boundedness 4 幕 + 要点卡 + 测验三视图；跑通全部验证层与改动任务测试。**验收点：用户评审判据讲法与画面后，再进 P2。**
- **P2 六大原理**：其余五家按 fix-list 逐条落记录（④ 只改律文、② 降格换真源、①⑤ 补例外降措辞、⑥ 拆假统一），24 幕全部由模型生成；旧场景下线留档。开工时先建常用动作（倒 / 切 / 装杯 / 撕纸等）的参照库与动作事实卡，验证层第 5 项同步启用。
- **P3 全量迁移**：按 P0 归并表将其余场景的内容抽入模型（抽取时同步定型与纠错，脏数据不平移），模式生成替换 autoBuild 与手写场景；重复场景合并。
- **P4 收尾**：旧 DB（FIRST_PRINCIPLES_DB 等）转为只读归档；全仓只剩一个内容源。

## 8. 日常修改 SOP（重写完成后长期执行）

### 8.1 改一条内容（台词/判据/口诀）
1. 在知识模型中按 ID 定位记录，只改该记录；
2. 跑校验（含例外冲突扫描），构建系统列出受影响的全部视图；
3. 一键重建受影响视图 + 跑验证层 2–5；
4. 提交 git，diff 即审查材料；用户抽查截图基线变化。

### 8.2 新增一幕
1. 先查模型：所需 Claim/Example 是否已有记录，无则先按 3.2 规范入库（分型、证据、例外齐全）；
2. 选模式、填节拍槽位（只引用 ID + 锚点 + 原语）；若用到新物理动作，先为该原语补参照图与动作事实卡，无卡不得开工；
3. 生成 → 验证层全过（含参照对比审查）→ 独立逻辑审查签字；旗舰幕另加第 7 项误读探针，通过后方可交付。

### 8.3 纠正一处理论错误
1. 按 8.1 改记录，并把推翻旧说法的反例登记为 Exception 或改判依据，留痕；
2. 校验器按引用关系列出全部受影响视图，逐一重建验证；
3. 若错误属「分型误判」（如联想曾标为规则），同步检查同批入库的同类记录。

### 8.4 角色与签字
- 编写（AI）：内容入库、场景生成、验证执行、审查材料整理。
- 审查（独立一遍，可由子代理）：只看截图与事实表，按五项清单找茬，不参与编写。
- 拍板（用户）：判据级改动（P0 类）、试点验收、基线更新。

### 8.5 参照与动作事实卡维护
1. 选参照：为动作找一张姿态/阶段清楚的真实照片（或视频截帧），图须能看清出口、接触与结果状态；存入参照库目录，登记 ID 与来源。
2. 提炼事实：从参照逐条写出 3–5 条因果事实（出口位置**与朝向**、接触关系、先后顺序、结束状态），一条一断言，可逐条判对错；禁止写「像在倒水」这类整体印象。
3. 挂接原语：事实卡 ID 写入对应原语与场景规格的 invariants；原语实现与事实冲突时改原语（一处），不逐幕打补丁。
4. 启用审查：该动作自此纳入验证层第 5 项（参照对比审查）；审查帧与参照图并排存档于该幕审查材料。
5. 更新：换参照或改事实须留痕（旧卡不删、标 superseded），并列出引用该卡的全部场景逐一复检。

## 9. 验收标准（总）

- 内容：试点家族全部 Claim 分型正确、例外齐备；清点报告 P0/P1 条目全部落实。
- 质量：insightcheck 不合格 0；截图基线经确认；逻辑审查无未决项；构建期断言全过；旗舰幕误读探针通过。
- 可维护性：改动任务测试五项全过（一个文件、一处编辑）；全仓同一说法只存一处（脚本扫描 KNOW 式副本为零）。

## 10. 风险与代价（明示）

- 内容层重建是最大工作量：现有各 DB 有重复、假词源、抄串，抽取时必须逐条定型纠错，不能平移——P0 归并统计后给出更准的工时估计。
- 模式化会让生成幕风格趋同：靠模式多样性 + 旗舰精调补，不在 P1 解决。
- 生成器与校验器是新增工具链，需要维护——但维护对象从 558 个场景收敛为「一模型 + 一套模式 + 一条流水线」，总维护面显著变小。
- 引擎层不动：本方案不换渲染技术（Remotion 等不解决逻辑与维护问题，已讨论定案）。
